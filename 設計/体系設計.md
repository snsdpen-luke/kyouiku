# コンピュータシステム教材 ── 体系設計（草案 v0.1）

作成: 2026-09-14 ／ 状態: **議論中の草案。未着手。** ／ 仮称: **ビット工房**

ラダー工房とは独立した別教材。ただし**作りの型（単一HTML・依存なし・通信なし・
Chromebookのタップ前提・版表示・自動判定・段階ヒント）は踏襲する**。
実績があり、生徒とChromebookの実態に合っているため。

---

## 0. 何を解こうとしているか

### ユーザーの要求

- 範囲: ネットワーク／データベース／セキュリティ／ビットコイン／電子マネー／
  タッチパネル／指紋認証／AI。**ハード・ソフト問わず幅広く**
- 成功条件（両方）:
  1. 生徒が**自分で組んで動かせる**
  2. 生徒が**「もっと知りたい」と言う**
- 学び方: **いろんな手段を使って**（つなぐ・攻める・数値をいじる・穴埋め、全部）
- 構成方針: **体系的に**

### この要求に潜む矛盾

「八つを幅広く」と「自分で組んで動かせる」は、そのままでは両立しない。
幅を取れば一つあたりが薄くなり、薄いものは組めない。

**解き方**: 幅と深さを**別の場所に分ける**。

- 深さ = **六段の階段**（部品を一つずつ、手で組んで覚える）→ 成功条件1
- 幅 = **またぎ課題**（覚えた部品を組み合わせて、身近な技術を再現する）→ 成功条件2

八つの題材は「八つの単元」ではなく、**階段の上に立つ八つの応用**になる。

## 1. 背骨 ── 六段の階段

段の順序は好みではなく**依存関係**で決まる。下がないと上が立たない。

| 段 | 動詞 | 覚える部品 | 生徒の問い |
|---|---|---|---|
| 0 | **表す** | 標本化・量子化・2進数・文字コード・色 | 世界を、どうやって数にする？ |
| 1 | **決める** | AND/OR/NOT・真理値表・加算器・レジスタ・命令 | 数から、どうやって答えを出す？ |
| 2 | **運ぶ** | 符号化・パケット・誤り検出・宛先・経路 | 数を、どうやって遠くへ届ける？ |
| 3 | **貯める** | 表・鍵（キー）・索引・照合 | 100万件から、どうやって一瞬で探す？ |
| 4 | **守る** | ハッシュ・鍵・署名・改ざん検知 | 見知らぬ相手を、どうやって信じる？ |
| 5 | **学ぶ** | 特徴量・重み・誤差・更新 | 答えを、どうやって自分で見つけさせる？ |

**5段が最後なのは、AIが下の全段を食って動くから。**
（世界を数にし＝0段、判定し＝1段、大量に貯め＝3段、遠くから集める＝2段）

---

## 2. またぎ課題 ── 体系が本物である証拠

一つの段に収まらない題材こそ、体系が実在する証拠になる。
収まる題材しか置けないなら、それは勝手に引いた線にすぎない。

| またぎ課題 | またぐ段 | 生徒が作るもの |
|---|---|---|
| **タッチパネル** | 0 | 指の位置 → 静電容量の変化 → 座標の数 |
| **指紋認証** | 0 → 1 → 4 | 画像 → 特徴点 → 照合 → 「元に戻せない」保存 |
| **パスワード** | 4 | ハッシュ保存・総当たり・なぜ平文で持たないか |
| **電子マネー** | 2 → 4 | 残高・署名・二重払いを止める仕組み |
| **ビットコイン** | 2 → 4（＋合意） | ハッシュの鎖・採掘・多数決 |
| **AIの判定** | 0 → 1 → 5 | 手書き文字か色か、特徴量 → 重み → 判定 |

**パスワード保存とビットコイン採掘は、同じ部品（ハッシュ）を正反対に使う。**
守るために使うか、賭けるために使うか。この対比を課題にする。

## 3. 共通エンジン ── 「部品に通す盤」

ラダー工房の心臓が `scanOnce`（PLCスキャン）だったように、この教材にも
一つの実行エンジンを置く。

```
[入力ブロック] → [部品] → [部品] → [出力ブロック]
                    ↑ ここに何を置くかで、段が変わる
```

- 0段: 波形 → 標本化 → 量子化 → ビット列
- 1段: ビット列 → AND/OR/NOT → 出力
- 2段: ビット列 → 誤り検出符号 → 雑音チャネル → 受信・検査
- 4段: ビット列 → ハッシュ → 比較
- 5段: 特徴量 → 重み付き和 → しきい値 → 判定

**一つのキャンバス、一つの実行エンジン、部品が増えるだけ。**
これが「体系的」の実装上の意味。

### 生徒の手の動き（四種、課題ごとに使い分ける）

| 手 | 使う場面 |
|---|---|
| **つなぐ** | 部品を線で結ぶ。全段の基本 |
| **攻める** | 総当たり・二重払い・衝突探し。仕組みを破って理解する |
| **回す** | しきい値・標本化周期・鍵長。壊れる境目を自分で見つける |
| **埋める** | 手順の欠けを埋める。順序の感覚 |

## 4. 既知の弱点（設計時点で判明・隠さない）

1. **共通エンジンを先に全層ぶん作ってはいけない。**
   ラダー工房は題材一つで945行。六段ぶんを机上で固めると破綻する。
   **一段で通してから広げる。**
2. **3段（貯める・DB）は「流れない」。**
   他段は「ビットが部品を通る」で描けるが、索引検索は「探す」であって
   「流す」ではない。同じ盤に載らない。**別の見せ方が要る。**
3. **ビットコインの「合意」は一本の線で描けない。**
   ノードが複数いる。パイプライン型の盤では表現できず、
   **複数ノードを並べる盤をもう一種類作る必要がある。**

## 6. 次の一手（提案）

**1段「決める」から着手する。**

理由:
- 共通エンジンを一番素直に酷使する段であり、ここで通れば型が決まる
- 真理値表による自動判定が作りやすい（ラダー工房の判定機構が流用できる）
- 0段（表す）は題材が魅力的だが、絵の作り込みが重く、エンジンの検証にならない
- ここで作った AND/OR/NOT は、2段・4段・5段でそのまま部品として再利用される

**一段が通ってから、次の段の設計に入る。**
